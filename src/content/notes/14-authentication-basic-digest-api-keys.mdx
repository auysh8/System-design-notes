{/* SECTION 2: 5 COMMON DEV CONFUSIONS */}
<div class="note-section">
    <div class="section-title">
        <span class="title-badge" style="background: var(--pastel-yellow);">2</span>
        Where Software Engineers Get Confused (5 Pitfalls)
    </div>

    <p>System design interviews frequently expose critical misunderstandings around authentication mechanisms. Here are the 5 foundational confusions disambiguated:</p>

    <div class="card-grid">
        <GoodNotesCard title="1. AuthN vs. AuthZ Frameworks" accent="pink">
            <p><strong>Confusion:</strong> Conflating identity verification with permissions.<br />
            <strong>Reality:</strong> <em>Authentication</em> proves <strong>identity</strong> ("Who are you?"). <em>Authorization</em> evaluates <strong>scopes & privileges</strong> (RBAC, ABAC, ACLs).</p>
        </GoodNotesCard>

        <GoodNotesCard title="2. Treating JWT as an Auth Type" accent="yellow">
            <p><strong>Confusion:</strong> Saying <em>"We use JWT authentication"</em>.<br />
            <strong>Reality:</strong> JWT is an open standard <strong>token format/carrier</strong> (RFC 7519), not an authentication mechanism itself. It simply carries claims.</p>
        </GoodNotesCard>

        <GoodNotesCard title="3. Confusing Bearer Auth & JWT" accent="blue">
            <p><strong>Confusion:</strong> Treating Bearer tokens and JWTs as synonymous.<br />
            <strong>Reality:</strong> <code>Bearer</code> is the <strong>HTTP Authorization transport scheme</strong>. A JWT is one specific structured payload carried inside the header.</p>
        </GoodNotesCard>

        <GoodNotesCard title="4. Calling OAuth 2 an Auth Method" accent="purple">
            <p><strong>Confusion:</strong> Claiming OAuth 2 is a login system.<br />
            <strong>Reality:</strong> OAuth 2 is a <strong>delegated authorization protocol</strong>. OpenID Connect (OIDC) is the identity layer on top that provides true authentication.</p>
        </GoodNotesCard>

        <GoodNotesCard title="5. Mixing Up SSO with Auth Protocols" accent="orange">
            <p><strong>Confusion:</strong> Viewing Single Sign-On as an isolated protocol.<br />
            <strong>Reality:</strong> <strong>Single Sign-On (SSO)</strong> is an identity management <em>architectural pattern</em> orchestrated via protocols like SAML 2.0 or OIDC.</p>
        </GoodNotesCard>
    </div>
</div>

    <StickyNote type="coral" title="⚠️ Major Security Flaws of Basic Auth:">
        <ul style="margin: 0.25rem 0 0 1.25rem; font-size: 0.9rem; line-height: 1.7;">
            <li><strong>Base64 is NOT Encryption:</strong> Base64 is a purely bidirectional encoding algorithm. Anyone intercepting the header can execute <code>atob("YWRtaW46c2VjcmV0MTIz")</code> in 1 millisecond.</li>
            <li><strong>Mandatory TLS:</strong> Basic Auth over unencrypted HTTP exposes credentials directly to packet sniffers on shared Wi-Fi.</li>
            <li><strong>Credential Resending:</strong> Browsers store the decoded credential pair in memory and automatically attach the header on every single subsequent request.</li>
            <li><strong>No Fine-Grained Expiry:</strong> Cannot expire or revoke individual tokens without resetting the user's primary password.</li>
        </ul>
    </StickyNote>

        <GoodNotesCard title="⚠️ Issue 1: Leak Risks" accent="pink">
            <p>If an API key is leaked (e.g. committed to public GitHub), <strong>anyone possessing the key</strong> can execute authorized operations until the developer manually revokes it in the dashboard.</p>
        </GoodNotesCard>

        <GoodNotesCard title="⏳ Issue 2: No Self-Contained Expiry" accent="yellow">
            <p>Unlike JWTs with standard <code>exp</code> timestamp claims, raw API keys are <strong>opaque strings</strong> without self-verifying expiration. Expiration and rotation schedules must be managed server-side.</p>
        </GoodNotesCard>

    <StickyNote type="sky" title="💡 Crucial Architectural Distinction: API Keys vs. JWT">
        <p style="font-size:0.95rem; line-height:1.6;">
            <strong>API Keys</strong> are <strong>opaque random identifiers</strong> requiring a server-side database/Redis lookup to identify the caller and verify permissions.<br />
            In contrast, <strong>JWTs</strong> are <strong>cryptographically signed payloads</strong> carrying serialized claims (user ID, expiration, roles) that any downstream service can verify statelessly without querying a central database.
        </p>
