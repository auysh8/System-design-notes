<div class="note-section">
    <p>A <mark class="hl-blue">Load Balancer</mark> distributes incoming client traffic across multiple backend servers to ensure no single server bears too much load, preventing bottlenecks and single points of failure (SPOF).</p>

    <StickyNote type="sky" title="❓ Core Question: How does a Load Balancer distribute traffic?">
        <p>Load balancers utilize <strong>7 core algorithms and strategies</strong> depending on server capacity, session requirements, and geographical proximity.</p>
    </StickyNote>
</div>

{/*  SECTION: 7 ALGORITHMS  */}
<div class="note-section">
    <div class="section-title">
        <span class="title-badge" style="background: var(--pastel-yellow);">7</span>
        Load Balancing Strategies & Algorithms
    </div>

    <div class="card-grid">

        {/*  1. Round Robin  */}
        <GoodNotesCard title="🔄 1. Round Robin" accent="pink">
            <p>Redirects incoming requests in sequential cyclical order: <mark class="hl-pink">Server 1 ➔ Server 2 ➔ Server 3 ➔ Server 1</mark>.</p>
            <div style="margin-top: 0.75rem; font-size: 0.85rem; color: var(--text-muted);">
                💡 <strong>Best for:</strong> Environments where all servers have identical hardware specifications and request processing times are uniform.
            </div>
        </GoodNotesCard>

        {/*  2. Least Connections  */}
        <GoodNotesCard title="🔗 2. Least Connections" accent="blue">
            <p>Redirects traffic to the server currently handling the <mark class="hl-blue">fewest active connections</mark>.</p>
            <div style="margin-top: 0.75rem; font-size: 0.85rem; color: var(--text-muted);">
                💡 <strong>Best for:</strong> Applications with long-lived persistent connections (e.g. WebSockets, streaming) where session lengths vary significantly.
            </div>
        </GoodNotesCard>

        {/*  3. Least Response Time  */}
        <GoodNotesCard title="⚡ 3. Least Response Time" accent="purple">
            <p>Redirects traffic to the server that is most responsive and serving responses with the <mark class="hl-purple">lowest latency</mark>.</p>
            <div style="margin-top: 0.75rem; font-size: 0.85rem; color: var(--text-muted);">
                💡 <strong>Best for:</strong> Providing the fastest response times when backend servers have different performance specs.
            </div>
        </GoodNotesCard>

        {/*  4. IP-Hash  */}
        <GoodNotesCard title="🔑 4. IP-Hash" accent="green">
            <p>Hashes the client's IP address to consistently map future requests from that IP to the <mark class="hl-green">exact same server</mark>.</p>
            <div style="margin-top: 0.75rem; font-size: 0.85rem; color: var(--text-muted);">
                💡 <strong>Best for:</strong> Session persistence (Sticky Sessions) when user state/session info is stored locally on a specific server and not synced across nodes.
            </div>
        </GoodNotesCard>

        {/*  5. Weighted Algorithms  */}
        <GoodNotesCard title="⚖️ 5. Weighted Algorithms" accent="yellow">
            <p>Servers are assigned <mark class="hl-yellow">weights based on capacity</mark>. Higher-capacity servers receive a proportionally larger share of traffic.</p>
            <div style="margin-top: 0.75rem; font-size: 0.85rem; color: var(--text-muted);">
                💡 <strong>Best for:</strong> Heterogeneous server clusters where nodes have different CPU, RAM, or network bandwidth specifications.
            </div>
        </GoodNotesCard>

        {/*  6. Geographical Algorithms  */}
        <GoodNotesCard title="🗺️ 6. Geographical Algorithms" accent="orange">
            <p>Redirects traffic to the server located closest to the user's <mark class="hl-orange">Geographical IP location</mark>.</p>
            <div style="margin-top: 0.75rem; font-size: 0.85rem; color: var(--text-muted);">
                💡 <strong>Best for:</strong> Global applications requiring latency reduction and localized content delivery (Geo-DNS routing).
            </div>
        </GoodNotesCard>

    </div>

    {/*  7. Consistent Hashing  */}
    <StickyNote type="lavender" title="⭕ 7. Consistent Hashing (Popular but Complex)">
        <p>Standard hashing (<code>Server = hash(key) % N</code>) breaks down when servers scale up or down because almost <strong>100% of keys get remapped</strong>. <mark class="hl-purple">Consistent Hashing</mark> solves this by mapping both servers and keys onto a circular ring topology.</p>
    </StickyNote>

    <StickyNote type="mint" title="❓ How does a Load Balancer know a server is offline?">
        <p>The load balancer constantly sends periodic <mark class="hl-green">Health Check ping requests</mark> (e.g., HTTP `/healthz` endpoints or TCP heartbeats) to all registered backend servers.</p>
        
        <ul style="margin: 0.75rem 0 0 1.25rem; font-size: 0.9rem;">
            <li><strong>Server Offline Detection:</strong> If a server fails to respond within a timeout window or returns error status codes, the load balancer automatically flags it as <mark class="hl-pink">UNHEALTHY</mark>.</li>
            <li><strong>Traffic Rerouting:</strong> It immediately stops sending traffic to the failed server and reroutes incoming requests to remaining active servers.</li>
            <li><strong>Auto-Recovery:</strong> It continues background probing, and once the server becomes active and healthy again, it re-introduces it into the server pool automatically.</li>
        </ul>
    </StickyNote>
