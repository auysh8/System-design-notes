<div class="note-section">

        <span class="title-badge" style="background: var(--pastel-green);">3</span>
        Schema Design & The Type System (SDL)
    </div>

    <p>
        GraphQL schemas are declared using the <mark class="hl-green">Schema Definition Language (SDL)</mark>. The schema acts as a strict contract specifying available types, fields, relationships, and executable entry points:
    </p>

    {/* VIBRANT SDL CODE STICKER */}
    <CodeSticker title="📜 schema.graphql — Strongly-Typed SDL Contract" copyLabel="Copy SDL">
```graphql
# 1. Custom Object Types
type User {
  id: ID!              # Non-null unique identifier
  name: String!        # Non-null string
  email: String         # Nullable string
  role: Role!           # Enum type
  posts: [Post!]!       # Non-null list containing non-null Post items
}

type Post {
  id: ID!
  title: String!
  author: User!
}

# 2. Enum Definition
enum Role {
  ADMIN
  MEMBER
  GUEST
}

# 3. Root Operations
type Query {
  user(id: ID!): User
  feed(limit: Int = 10): [Post!]!
}

type Mutation {
  createPost(input: CreatePostInput!): Post!
}

# 4. Dedicated Input Object
input CreatePostInput {
  title: String!
  authorId: ID!
}
```
    </CodeSticker>

<div class="note-section">
    <div class="section-title">
        <span class="title-badge" style="background: var(--pastel-pink);">5</span>
        Error Handling: The 200 OK Envelope & Partial Failures
    </div>

    <p>
        Unlike REST APIs that rely on HTTP transport status codes (404, 500), <mark class="hl-pink">GraphQL requests almost always return HTTP 200 OK</mark>. Errors are treated as first-class domain values embedded inside the response payload envelope:
    </p>

    {/* EXPLANATORY STICKY NOTE */}
    <StickyNote type="lavender" title="💡 Why HTTP 200 OK for Execution Errors?">
        <p style="font-size: 0.92rem; line-height: 1.6; margin-bottom: 0.4rem;">
            Because a GraphQL query can resolve <strong>multiple independent entity branches</strong> simultaneously, execution can be <em>partially successful</em>. For example, a user's core profile resolves successfully from Redis, but their external payment gateway lookup times out.
        </p>
        <p style="font-size: 0.88rem; font-weight: 700; color: #7e22ce; margin: 0;">
            ➔ HTTP 200 signifies the transport layer succeeded; the client inspects <code>errors[]</code> to gracefully handle field-level fallbacks.
        </p>
    </StickyNote>

    <p>Essential patterns for scaling and hardening GraphQL APIs in high-throughput production environments:</p>

    {/* PRODUCTION BEST PRACTICES CARDS */}
    <div class="card-grid">
        
        <GoodNotesCard title="⚡ 1. DataLoader (Batching & In-Memory Caching)" accent="green">
            <p>
                Solves the server-side N+1 database problem by collecting individual resolver IDs across a single tick of the event loop and dispatching a single batch SQL query:
            </p>
            <div style="background: var(--paper-bg); border-left: 3px solid var(--pastel-green-dark); padding: 0.4rem 0.65rem; font-family: var(--font-code); font-size: 0.78rem; margin-top: 0.5rem;">
                <code>SELECT * FROM users WHERE id IN (1, 2, 3...);</code>
            </div>
        </GoodNotesCard>

        <GoodNotesCard title="🧩 2. Schema Modularity & Federation" accent="purple">
            <p>
                Avoid monolithic megaschemas. Decompose domains using <strong>Apollo Federation</strong> or schema stitching where independent subgraphs join seamlessly under a unified gateway.
            </p>
        </GoodNotesCard>

        <GoodNotesCard title="📦 3. Use Input Objects for Mutations" accent="blue">
            <p>
                Always encapsulate mutation arguments in dedicated <code>input</code> types (e.g. <code>input UpdateUserInput &#123; ... &#125;</code>) to preserve backwards compatibility when adding optional parameters.
            </p>
        </GoodNotesCard>

        <GoodNotesCard title="🛑 4. Max Query Depth Limiting" accent="pink">
            <p>
                Prevent malicious or accidental deeply nested circular queries (e.g. <code>user ➔ posts ➔ author ➔ posts ➔ author...</code>) by rejecting queries exceeding a max depth (e.g., limit = 5 levels).
            </p>
        </GoodNotesCard>
