{/* SECTION 3: SCHEMA DESIGN & TYPE SYSTEM */}
<div class="note-section">
    <div class="section-title">
        <span class="title-badge" style="background: var(--pastel-blue);">3</span>
        Schema Design & The Type System (SDL)
    </div>

    <p>GraphQL is strictly typed. The server defines a strongly-typed contract using the <mark class="hl-blue">Schema Definition Language (SDL)</mark>:</p>

    <StickyNote type="sky" title="📜 Schema Definition Language (SDL) Example:">
        <div style="background: #1e1e24; color: #f1f5f9; border-radius: 8px; padding: 1.15rem; font-family: var(--font-code); font-size: 0.88rem; margin-top: 0.5rem;">
            <pre style="margin: 0; color: #f8fafc; line-height: 1.5;"><code><span style="color:#a855f7; font-weight:700;">type</span> <span style="color:#38bdf8; font-weight:700;">User</span> &#123;<br />  <span style="color:#e2e8f0;">id</span>: <span style="color:#f59e0b;">ID!</span><br />  <span style="color:#e2e8f0;">name</span>: <span style="color:#f59e0b;">String!</span><br />  <span style="color:#e2e8f0;">posts</span>: [<span style="color:#38bdf8;">Post!</span>]!<br />&#125;<br /><br /><span style="color:#a855f7; font-weight:700;">type</span> <span style="color:#38bdf8; font-weight:700;">Query</span> &#123;<br />  <span style="color:#e2e8f0;">user</span>(<span style="color:#f59e0b;">id</span>: <span style="color:#f59e0b;">ID!</span>): <span style="color:#38bdf8;">User</span><br />&#125;<br /><br /><span style="color:#a855f7; font-weight:700;">type</span> <span style="color:#38bdf8; font-weight:700;">Mutation</span> &#123;<br />  <span style="color:#e2e8f0;">createUser</span>(<span style="color:#f59e0b;">name</span>: <span style="color:#f59e0b;">String!</span>): <span style="color:#38bdf8;">User</span><br />&#125;</code></pre>
        </div>
    </StickyNote>

    <div class="card-grid" style="margin-top: 1.25rem;">
        <GoodNotesCard title="❗ Non-Null Modifier (!)" accent="yellow">
            <p>An exclamation point (e.g. <code>String!</code>) guarantees the field will <strong>never be null</strong>. If the resolver returns null, GraphQL raises a schema execution error.</p>
        </GoodNotesCard>

        <GoodNotesCard title="📦 List Types ([Post!])" accent="purple">
            <p>Square brackets denote an array of objects. <code>[Post!]!</code> ensures both the list itself and every element inside the list are non-null.</p>
        </GoodNotesCard>
    </div>
</div>

{/* SECTION 5: ERROR HANDLING & 200 OK PARADIGM */}
<div class="note-section">
    <div class="section-title">
        <span class="title-badge" style="background: var(--pastel-pink);">5</span>
        GraphQL Error Handling: The 200 OK Paradigm
    </div>

    <p>GraphQL error handling differs fundamentally from REST APIs: <mark class="hl-pink">GraphQL requests almost always return HTTP 200 OK</mark> at the transport layer, even when field-level execution errors occur.</p>

    <StickyNote type="lavender" title="⚠️ Why 200 OK for Errors?">
        <p style="font-size:0.95rem; line-height:1.6;">
            Because a single GraphQL query can resolve multiple independent fields, one field might succeed (e.g. <code>user.name</code>) while another fails (e.g. <code>user.paymentDetails</code>). The HTTP status code represents the <strong>transport handshake</strong>, while the payload contains partial data alongside an <code>errors</code> array.
        </p>
    </StickyNote>

{/* SECTION 7: GRAPHQL BEST PRACTICES */}
<div class="note-section">
    <div class="section-title">
        <span class="title-badge" style="background: var(--pastel-yellow);">7</span>
        GraphQL Production Best Practices & Security
    </div>

    <p>Handwritten guidelines for resilient, secure, and performant GraphQL schemas:</p>

    <div class="card-grid">
        <GoodNotesCard title="📦 1. Keep Schemas Small & Modular" accent="purple">
            <p>Deconstruct massive monolithic schemas into domain-driven type modules or federated subgraphs (e.g. Apollo Federation).</p>
        </GoodNotesCard>

        <GoodNotesCard title="🏷️ 2. Use Meaningful Naming" accent="blue">
            <p>Adopt clear, domain-aligned camelCase for fields and PascalCase for types. Avoid vague, overloaded names.</p>
        </GoodNotesCard>

        <GoodNotesCard title="📝 3. Use Input Types for Mutations" accent="green">
            <p>Wrap mutation parameters into dedicated <code>input</code> objects (e.g. <code>input CreateUserInput &#123; ... &#125;</code>) to preserve backwards compatibility.</p>
        </GoodNotesCard>

        <GoodNotesCard title="🛑 4. Avoid Deeply Nested Queries" accent="yellow">
            <p>Unconstrained circular references (e.g. <code>user ➔ posts ➔ author ➔ posts</code>) can easily crash downstream databases.</p>
        </GoodNotesCard>
    </div>

    <StickyNote type="coral" title="🛡️ Critical Defense: Implement Query Depth & Complexity Limits">
        <p style="font-size:0.95rem; line-height:1.6;">
            Always enforce strict <strong>max query depth</strong> (e.g. max depth of 5 levels) and calculate <strong>query cost complexity analysis</strong> at the gateway before delegating execution to resolvers, shielding your database from denial-of-service (DoS) attacks.
        </p>
    </StickyNote>
</div>
